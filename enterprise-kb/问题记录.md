## 问题 1：Node.js 版本不兼容

**日期**：2026-07-20

**现象**：`npm install` 报错
```
npm error EBADENGINE
npm error Not compatible with your version of node/npm: open-webui@0.10.2
npm error Required: {"node":">=18.13.0 <=22.x.x"}
npm error Actual:   {"node":"v24.15.0"}
```

**原因**：本地 Node.js v24 超过了项目要求的 v22 上限，npm 新版默认强制检查 engine 版本。

**解决方案**：
```bash
npm install --engine-strict=false
```
v24 API 向下兼容，实际运行无任何问题。

**教训**：大型开源项目 package.json 的 engine 限制不一定及时更新，遇到类似问题先尝试 `--engine-strict=false`。

## 问题 2：WEBUI_SECRET_KEY 未设置导致启动失败

**日期**：2026-07-20

**现象**：直接运行 uvicorn 启动后端报错：
```
WEBUI_SECRET_KEY is not set. It is a hard requirement when authentication is enabled.
```

**原因**：项目在认证模式下要求必须设置 `WEBUI_SECRET_KEY` 环境变量。Docker 部署时自动生成，手动启动需要自己设置。

**解决方案**：
```bash
WEBUI_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')" \
python -m uvicorn open_webui.main:app --host 127.0.0.1 --port 8080
```

**教训**：读开源项目代码时要关注环境变量依赖，`.env.example` 里不一定写了所有必需的变量。

## 问题 3：HuggingFace 模型下载失败（国内网络）

**日期**：2026-07-20

**现象**：服务启动后卡在 `Fetching 30 files`，最终报错：
```
Cannot determine model snapshot path: An error happened while trying to 
locate the file on the Hub and we cannot find the requested files in the
```

**解决方案**：设置 HuggingFace 镜像：

**教训**：在国内做 AI 开发，HuggingFace、GitHub 等资源都要考虑网络问题，提前准备镜像方案。

## 问题 4：代码修改后前端不生效

**日期**：2026-07-20

**现象**：修改 Svelte 组件后刷新浏览器看不到变化。

**原因**：FastAPI 以静态文件方式 serve `build/` 目录的前端产物。修改源码后必须重新 `npm run build` 才会更新 `build/` 目录。

**解决方案**：
```bash
npm run build        # 重新构建前端
# 然后重启后端
```

**教训**：SvelteKit adapter-static 模式下是纯静态导出，没有 HMR。开发时可以用 `npm run dev` 开启 Vite 开发服务器获得热更新，但需要额外配置 CORS 代理。

## 问题 6：端口被占用 `[winerror 10048]`

**日期**：2026-07-20

**现象**：重启服务时报错：
```
error while attempting to bind on address ('127.0.0.1', 8080): 
[winerror 10048] 通常每个套接字地址只允许使用一次
```

**原因**：上一次的后台进程没有完全退出，端口 8080 仍被占用。

**解决方案**：
```bash
# 查找占用端口的进程
netstat -ano | grep ":8080" | grep LISTENING
# 杀掉进程
taskkill //PID <进程ID> //F
```

**教训**：后台启动 uvicorn 后关终端不会自动杀进程，需要手动清理。写个启动脚本自动检测端口会更好。

## 问题 7：Tab 导航不跨页面显示

**日期**：2026-07-20

**现象**：Tab 导航放在 `[id]/+page.svelte` 里，切到 `/chunks` 页面后 Tab 消失了。

**原因**：SvelteKit 的 `+page.svelte` 只作用于当前路由。子页面 `/chunks` 有自己独立的 `+page.svelte`，不会继承父页面的 UI。

**解决方案**：改用 `+layout.svelte`，通过 `<slot />` 让 Tab 导航在所有子页面共享：
```
[id]/
  +layout.svelte     ← Tab 导航 + <slot />
  +page.svelte       ← Files 视图
  chunks/+page.svelte ← Chunks 视图
```

**教训**：SvelteKit 的 layout 机制是共享 UI 的正确方式。page 只渲染自身内容，跨页面共享的 UI（导航栏、侧边栏）必须放在 layout 里。

## 问题 8：`add_file_to_knowledge_by_id` 中进度钩子没触发

**日期**：2026-07-20

**现象**：通过 Web UI 上传文件到知识库后，Processing 页面始终显示 "No processing tasks yet"。

**排查过程**：
1. 检查前端 API 调用 → 正常，`/progress` 返回 `[]`
2. 检查数据库 → `knowledge_processing_task` 表为空
3. 检查 `add_file_to_knowledge_by_id` 端点 → 确认有 `_update_processing_progress` 调用
4. 抓前端上传时的网络请求 → 发现上传走的是 `/api/v1/files/` 端点，不是 `/api/v1/knowledge/{id}/file/add`

**原因**：Web UI 上传文件时，流程是：
```
POST /api/v1/files/ (带 metadata.knowledge_id)
  → process_uploaded_file() 
    → 内部直接调用 process_file() + Knowledges.add_file_to_knowledge_by_id()
    → 绕过了 routers/knowledge.py 中的进度钩子
```
我的进度追踪代码只加在了 `routers/knowledge.py` 的 `add_file_to_knowledge_by_id` 函数里，但 Web UI 上传流程根本不走这个端点，而是走 `routers/files.py` 的内部逻辑。

**解决方案**：在 `routers/files.py` 的 `process_uploaded_file()` 中也加入同样的进度追踪代码。

**教训**：在已有项目上做增量开发时，**必须追踪完整的数据流**，不能假设用户只通过某个 API 端点操作。同一个功能可能有多个入口（API 调用、Web UI 上传、批量导入），每个入口都要覆盖到。

## 问题 10：SQLite WAL 模式下的数据恢复

**日期**：2026-07-20

**现象**：直接 DELETE 数据库中的用户数据后，想恢复时发现没有 `.bak` 备份文件。

**原因**：SQLite WAL（Write-Ahead Log）模式下，数据修改可能还在 WAL 文件中未完全合并到主 DB 文件。执行 `PRAGMA wal_checkpoint(TRUNCATE)` 可以强制合并。

**教训**：操作数据库前先备份，尤其是生产环境。SQLite 虽然有 WAL 保护，但不能替代备份。

## 问题 11：`query_collection` 参数名和返回值格式不对

**日期**：2026-07-20

**现象**：调用 evaluate/query API 时报错：
```
query_collection() got an unexpected keyword argument 'query'
```

**原因**：`query_collection()` 的实际签名是 `(request, collection_names, queries, embedding_function, k)`，其中 `queries` 是 list[str] 且必须传入 `embedding_function`。而我写成了 `query=form_data.query, user=user`。

修复参数后仍返回空结果，进一步发现返回值格式也不同：返回的是 dict 格式 `{'documents': [[]], 'distances': [[]], 'metadatas': [[]]}`，没有 `ids` 字段。

**解决方案**：
```python
# 正确调用
result = await query_collection(
    request=request,
    collection_names=[id],
    queries=[form_data.query],       # list, not str
    embedding_function=request.app.state.EMBEDDING_FUNCTION,  # required
    k=k,
)
# 正确解析
docs = result.get('documents', [[]])[0]
dists = result.get('distances', [[]])[0]
```

**教训**：调用开源项目内部函数时，不要凭经验猜参数和返回值。先用 grep 找到函数定义，确认签名和返回格式。

## 问题 22：校验员反馈检索结果不完整——chunk 碎片化+多层截断

**日期**：2026-07-31

**现象**：校验员 Agent 输出"后续内容被截断"，只能看到文档标题和半句话，无法验证分析结论是否与原文一致。

**排查过程**：
1. 检查截断值：每篇文档 `[:1500]` → 变量传递 `[:2000]` → prompt `[:4000]` → LLM 输出 `1024 tokens`
2. 查 DB 发现 chunk 平均只有 **202 字符**，最大才 1004 字符
3. 检索 k=3 时最多拿到 ~600 字符碎片，即使不截断也远远不够

**原因**：
- ChromaDB 里每个 chunk 本身就是小片段（分块产物），k=3 检索 3 个 chunk 总计 ~600 字
- 上层还有多层截断进一步压缩
- 校验员看到的是 3 个互不关联的碎片，根本无法做一致性判断

**解决方案**：
1. 检索量从 k=3 提升到 **k=15**
2. 用 `OrderedDict` 按 `file_id` 分组，组内按 `chunk_index` 排序后拼接成连贯文档
3. 全面提权截断值：doc 1500→4000、变量 2000→6000、变量替换 3000→8000、prompt 4000→10000、max_tokens 1024→2048
4. 校验员默认提示词重写为 5 步核查流程（✅一致/❌不一致/⚠️未提及 + 引用原文证据 + 总体评分）

**教训**：RAG 场景下不能假设检索结果足够完整。chunk 碎片化是多步 Agent 的常见陷阱——检索员→分析员→校验员链路中每个环节都在丢失信息。解决思路：源头扩大检索量 + 智能合并 + 全链路提权截断。

**涉及文件**：`backend/open_webui/routers/knowledge.py`、`backend/open_webui/models/knowledge.py`

## 问题 24：Alembic 多头冲突導致启动失败

**日期**：2026-07-31

**现象**：`python -m uvicorn open_webui.main:app` 报错 `MultipleHead: Multiple heads are present for given argument 'head'; b8c9d0e1f2a3, c9d03e6dd01f`

**原因**：
- `a7b8c9d0e1f2`（KB 管理表）→ `b8c9d0e1f2a3`（Agent 工作流表）

2. 手动更新 `alembic_version` 表到 `b8c9d0e1f2a3`（所有表已在旧迁移中创建）

**教训**：合并迁移（merge migration）之后创建的新迁移必须指向合并版本，否则 Alembic 会认为存在两个 head 分支。

## 问题 16：分块合并偶尔失败——`findIndex` 和 `chunk_index` 混用

**日期**：2026-07-21

**现象**：选中两个相邻分块点 Merge，有时成功有时失败。

**原因**：前端用 `chunks.findIndex()` 取数组下标作为 `start_index`/`end_index` 发给后端，但后端用 `chunk_index` 字段做 WHERE。一旦合过某分块，`chunk_index` 出现间隙（如 0,1,3,4），数组下标 `[2,3]` 和 DB 值 `[3,4]` 对不上。

**修复**：改为用 `chunk.chunk_index`（数据库值）传给 API。

**教训**：跨越前后端边界的参数，一律用数据库字段值，不能用数组位置。

## 问题 17：SQLite UNIQUE 约束——merge/split 时 chunk_index 中间态冲突

**日期**：2026-07-21

**现象**：merge 和 split 后端 API 返回 500，日志显示 `IntegrityError: UNIQUE constraint failed: knowledge_chunk.file_id, knowledge_chunk.chunk_index`。

**原因**：`knowledge_chunk` 表有 `UNIQUE(file_id, chunk_index)` 约束。merge/split 后需要重编号后续分块——当 UPDATE 按 ASC 顺序修改 chunk_index 时，中间态会与尚未更新的分块冲突。

例如 5 个分块 [0,1,2,3,4]，合并 0+1 后剩余 [0(新),2,3,4]，重编号为 [0,1,2,3]：
```
SET chunk_index=1 WHERE ... (old=2) → [0,1,1,3,4] ← 冲突！两个 chunk_index=1
```
SQLite 逐条执行 UPDATE，第一条就撞上还没更新的索引 1 的分块。

**尝试过的失败方案**：
- `await db.flush()` 在 DELETE 和 UPDATE 之间——flush 只清理 ORM state，不解决 SQL 层冲突
- 倒序 DESC UPDATE——仍然冲突（3→2 撞上还没移的 2）
- 两轮赋负值再正序——SQLAlchemy async flush 后对象 detached，第二轮赋值无效

**最终解决方案**：用原始 SQL 把所有 chunk_index 偏移 +10000（安全区），flush 后再用 ORM 按 ASC 重新编号 0,1,2...：
```python
# Step 1: 全部进入安全区（10000+）
await db.execute(sa_text(
    "UPDATE knowledge_chunk SET chunk_index = chunk_index + 10000 "
    "WHERE knowledge_id = :kid AND file_id = :fid"
))
await db.flush()
# Step 2: 重新编号（所有值 ≥10000，与 0..N 无冲突）
for i, c in enumerate(result.scalars().all()):
    c.chunk_index = i
```

**教训**：
1. SQLite 不支持延迟约束检查（不像 PostgreSQL 的 `DEFERRABLE`），UNIQUE 约束在每条语句执行时立即检查
2. ORM 的 flush/refresh 机制在异步模式下行为不可靠——混合使用原始 SQL + ORM 是最稳妥的方案
3. 涉及唯一约束的批量 UPDATE，必须保证中间态也不违反约束

**涉及文件**：`backend/open_webui/routers/knowledge.py` — `merge_knowledge_chunks` 和 `split_knowledge_chunk`

## 问题 18：reindex 报 TypeError——`save_docs_to_vector_db` 调用方式错误

**日期**：2026-07-21

**现象**：点 Reindex Vectors 返回 500，日志：`TypeError: save_docs_to_vector_db() got an unexpected keyword argument 'bypass_embedding'`

**原因**：犯了三个错误：
1. 传了不存在的参数 `bypass_embedding=False`
2. 用 `await` 调用了一个同步函数
3. 缺少必需参数 `config: RetrievalConfig`

实际上 `save_docs_to_vector_db` 是同步函数，需要 `run_in_threadpool` 包装。

**修复**：
```python
# 错误
await save_docs_to_vector_db(request=request, collection_name=id,
    docs=docs, user=user, bypass_embedding=False)

# 正确
from fastapi.concurrency import run_in_threadpool
config = await get_retrieval_config()
await run_in_threadpool(save_docs_to_vector_db,
    request, docs, id, config, None, True, True, False, user)
```

**教训**：调用项目内部函数前没有确认是同步还是异步，也没有确认完整参数列表。grep 函数定义确认签名是最基本的操作。

## 问题 25：OPENAI_API_BASE_URL 被无条件覆盖——embedding 连到 api.openai.com

**日期**：2026-08-14

**现象**：压测上传场景，`file/add` 报 400，日志显示 `Cannot connect to api.openai.com`。但 `.env` 里明明把 `OPENAI_API_BASE_URL` 设成了 mock 地址 `http://127.0.0.1:9099/v1`。

**教训**：开源项目的配置加载顺序很隐晦——变量可能在 import 阶段被硬编码覆盖。改配置前先 grep 该变量在 config.py 里的所有赋值点，别只看 `.env`。

## 问题 26：Files.upload 后台内容提取竞态——file/add 报 EMPTY_CONTENT

**日期**：2026-08-14

**现象**：压测上传场景，`Files.upload` 成功返回后紧跟 `file/add`，大量报 400 `EMPTY_CONTENT`（内容为空）。

**原因**：`Files.upload` 默认 `process_in_background=true`，内容提取（分块）在后台任务异步执行。压测脚本上传完立刻调 `file/add`，此时 `file.data['content']` 还没提取完，为空 → 400。

**解决方案**：上传时带 `?process_in_background=false`，让「分块 + 向量化」在上传阶段同步完成，`file/add` 时 content 已就绪。

**教训**：两段式接口（上传 → 入库）之间若夹着后台任务，会引入竞态。压测脚本必须显式同步化，否则测出来的是竞态失败而非真实瓶颈。

## 问题 27：相同内容去重——file/add 报 DUPLICATE_CONTENT

**日期**：2026-08-14

**现象**：压测上传场景，3 个用户上传相同内容的文件后，`file/add` 报 400 `DUPLICATE_CONTENT`。

## 问题 28：Locust catch_response 缺失——r.failure() 抛 LocustError

**日期**：2026-08-14

**现象**：Locust 脚本在登录失败分支调用 `r.failure()` 时崩溃：`LocustError: Attempting to set status on a request that has not yet been made`。

**原因**：`r.failure()` 只能在 `with self.client.post(..., catch_response=True) as r:` 上下文里调用，否则响应对象还没进入「可标记」状态。

**解决方案**：给登录请求加 `catch_response=True`，把 `r.failure(...)` 放进 `with ... as r:` 块内。

## 问题 29：ChromaDB PersistentClient 多 worker 写坏 HNSW 索引——file/add 51.92% 失败

**日期**：2026-08-14

**现象**：100 并发保压下，`KB.file_add` 失败率高达 **51.92%（27/52）**，平均耗时 11 秒、P95 37 秒。后端日志刷屏：

```
Error in compaction: Error constructing hnsw segment reader:
  Error creating hnsw segment reader: Error loading hnsw index
Error sending message to compactor
Error processing file: 0eae871e-...
```

**原因**：二次开发用的是 ChromaDB `PersistentClient`（进程内嵌入，数据落在本地 `vector_db/` 的 SQLite + HNSW 文件）。单 worker 开发模式没问题，但切 4 worker 后，多个 uvicorn 进程**同时读写同一份 Chroma 本地文件，无跨进程锁**，导致 HNSW 索引损坏、compactor 后台线程崩溃，`file/add` 在「写向量」步骤抛异常。

**解决方案（已解决，已验证）**：起独立 Chroma server（`chroma run`），4 worker 通过 HTTP 连同一服务，由服务端单进程串行化写入——即 `.env` 设 `CHROMA_HTTP_HOST`/`CHROMA_HTTP_PORT`，走 `chromadb.HttpClient`（代码见 `retrieval/vector/dbs/chroma.py`，`CHROMA_HTTP_HOST` 非空即切 HTTP 客户端）。

**验证结果**：切远程 Chroma 后复跑上传压测——10 并发 `KB.file_add` **0 失败**（41 请求全成功，之前 51.92%）；Chroma server 日志 0 个 HNSW/compaction 错误。并发写损坏彻底消除。

**教训**：
1. 本地嵌入式的向量库（Chroma PersistentClient、FAISS 等）**不是多进程安全的**，切多 worker 部署必须换「独立服务 + HTTP 客户端」模式。
2. 并发写损坏在单 worker 下永远复现不了，只有多进程压测才能暴露——这正是「模拟生产环境」压测的价值。

**涉及文件**：`backend/open_webui/retrieval/vector/dbs/chroma.py`、`open-webui/.env`

## 问题 30：内嵌 Chroma 吃满 Windows 提交内存——OpenBLAS 分配失败 / bash fork 1455

**日期**：2026-08-14

**现象**：压测后 `import chromadb` 报 `OpenBLAS error: Memory allocation still failed after 10 retries`，bash fork 报 `CreateFileMapping cygpid.xxx, Win32 error 1455`。但物理内存还有 4.4 GB 空闲。

**原因**：Windows 的**提交限制（commit limit = 物理内存 + 分页文件）**被打满——`FreeVirtualMemory` 只剩 **73 MB**。4 个 OWUI worker 各自内嵌一份 Chroma（HNSW 索引 memory-mapped），共吃掉约 **54 GB 虚拟内存 commit**。

**验证**：停掉 OWUI 后，`FreeVirtualMemory` 从 73MB 回升到 54GB，物理内存从 4.4GB 回到 6GB。

**解决方案（已解决）**：同问题 #29——切远程 Chroma，让索引只在一个服务进程里加载一份，而不是每 worker 一份。切完后 OWUI 4 worker 均走 `chromadb.HttpClient`，不再各自内嵌 Chroma。

**教训**：内存问题不能只看「物理内存剩余」，Windows 下 `FreeVirtualMemory`（提交额度）耗尽同样会导致分配失败，且现象诡异（Python 库报错、fork 报错，看似毫不相关）。

**涉及文件**：`backend/open_webui/retrieval/vector/dbs/chroma.py`

## 问题 31：20 并发上传触发 Windows select() 512 FD 上限——mock 连接失败/描述符耗尽

**日期**：2026-08-14

**现象**：切远程 Chroma 后，把上传压测拉到 20 并发，`KB.file_add` 失败率又涨到 ~48%（72 个 400 + 2 个 500）。但 OWUI 日志里已无 HNSW 错误，取而代之的是：

```
ClientConnectorError: Cannot connect to host 127.0.0.1:9099
ValueError: too many file descriptors in select()
```

**原因**：这是**测试环境的两个新瓶颈叠加**，跟 Chroma 无关（Chroma server 日志 0 错误）：
1. **Windows `select()` 512 FD 上限**：OWUI 用 SelectorEventLoop（psycopg async 需要），Windows 下 `select()` 最多管 512 个 socket。20 并发上传 × 多 chunk 嵌入，一个 worker 的事件循环撑到 512 个连接后 `select()` 直接抛错。
2. **单进程 mock 成为瓶颈**：mock embedding（9099）是单进程 FastAPI，20 并发下连接堆积、accept backlog 打满，OWUI 连不上它。

**验证**：降到 10 并发复跑，`KB.file_add` **0 失败**（41 请求全成功），无新 FD 错误——说明 Chroma 修复有效，10 并发是当前压测环境的稳定工作点。

**教训**：
1. **压测是「打地鼠」**——修掉一个瓶颈，下一个立刻浮现。修 Chroma 后暴露的是 mock + Windows FD 上限，这正好印证方案里预判的「隐患 #5：mock 自身成为瓶颈」。
2. **Windows 不是压测的好宿主**：`select()` 512 FD 上限是 Windows 独有（Linux 用 epoll 无此限制），生产部署在 Linux 上不会踩。压测要区分「真实系统瓶颈」和「测试宿主限制」。
